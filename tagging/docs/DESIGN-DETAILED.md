## 1. Schema (PostgreSQL)

The Flyway migration `src/main/resources/db/migration/postgresql/V1__init.sql` (an H2 twin lives
beside it for tests). Every shard runs the same schema; `JdbcSchema.migrate` applies it per shard at
startup.

```sql
CREATE TABLE tags (
    tenant_id   VARCHAR(64)  COLLATE "C" NOT NULL,
    tag_id      BIGINT       NOT NULL,                 -- Snowflake id, unique across shards
    name        VARCHAR(256) NOT NULL,                 -- as typed
    name_norm   VARCHAR(256) COLLATE "C" NOT NULL,     -- NFKC, trimmed, spaces collapsed, lower-case
    color       VARCHAR(16),
    version     BIGINT       NOT NULL,                 -- ETag; CAS on update
    deleted     BOOLEAN      NOT NULL DEFAULT FALSE,
    created_by  VARCHAR(128),
    created_at  TIMESTAMPTZ  NOT NULL,
    updated_at  TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_tags PRIMARY KEY (tenant_id, tag_id)
) WITH (fillfactor = 90);                              -- room for HOT updates on rename/recolor
CREATE UNIQUE INDEX ux_tags_name ON tags (tenant_id, name_norm);

CREATE TABLE entities (                                -- dense ids for bitmaps and cursors
    tenant_id   VARCHAR(64)  COLLATE "C" NOT NULL,
    entity_type VARCHAR(40)  COLLATE "C" NOT NULL,     -- "jira:issue", "confluence:page"
    entity_id   VARCHAR(128) COLLATE "C" NOT NULL,     -- the product's id, opaque to us
    entity_seq  BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    CONSTRAINT pk_entities PRIMARY KEY (tenant_id, entity_type, entity_id)
);
CREATE UNIQUE INDEX ux_entities_seq ON entities (tenant_id, entity_seq);

CREATE TABLE entity_tags (
    tenant_id   VARCHAR(64)  COLLATE "C" NOT NULL,
    entity_type VARCHAR(40)  COLLATE "C" NOT NULL,
    entity_id   VARCHAR(128) COLLATE "C" NOT NULL,
    tag_id      BIGINT       NOT NULL,
    entity_seq  BIGINT       NOT NULL,                 -- denormalized from entities: the reverse index needs it
    created_by  VARCHAR(128),
    created_at  TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_entity_tags PRIMARY KEY (tenant_id, entity_type, entity_id, tag_id)
) PARTITION BY HASH (tenant_id);                       -- 16 partitions, created by a DO block
CREATE INDEX ix_entity_tags_by_tag ON entity_tags (tenant_id, tag_id, entity_seq);

CREATE TABLE tag_usage (                               -- sharded counter
    tenant_id VARCHAR(64) COLLATE "C" NOT NULL,
    tag_id    BIGINT      NOT NULL,
    bucket    SMALLINT    NOT NULL,                    -- 0..usage-buckets-1, random per write
    cnt       BIGINT      NOT NULL,
    CONSTRAINT pk_tag_usage PRIMARY KEY (tenant_id, tag_id, bucket)
) WITH (fillfactor = 70);

CREATE TABLE outbox (
    seq        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,   -- the consistency token
    tenant_id  VARCHAR(64) NOT NULL,
    event_type VARCHAR(32) NOT NULL,
    payload    TEXT        NOT NULL,                   -- JSON TagEvent
    created_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE outbox_relay_state (                      -- one row: the relay lock and the exact watermark
    id         INT         PRIMARY KEY,
    last_seq   BIGINT      NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);
INSERT INTO outbox_relay_state (id, last_seq, updated_at) VALUES (1, 0, now());

CREATE TABLE idempotency_keys (
    tenant_id    VARCHAR(64)  COLLATE "C" NOT NULL,
    idem_key     VARCHAR(128) COLLATE "C" NOT NULL,
    request_hash VARCHAR(64)  NOT NULL,                -- SHA-256 of the canonical request
    response     TEXT         NOT NULL,                -- '' while claimed, the response after
    created_at   TIMESTAMPTZ  NOT NULL,
    CONSTRAINT pk_idempotency_keys PRIMARY KEY (tenant_id, idem_key)
);
CREATE INDEX ix_idempotency_created ON idempotency_keys (created_at);
```

### 1.1 Why each choice

| Choice | Reason |
|---|---|
| `tenant_id` first in every PK | A tenant's rows are contiguous in every B-tree; every query is a range on one tenant; Citus can distribute every table by `tenant_id` with co-location, so joins stay local |
| No foreign keys | They'd add a lock per insert on the referenced row (a hot tag would serialize). The service guarantees references (`requireLive` in the same transaction) and the purge job cleans up |
| Tombstone name instead of a partial unique index | On delete, `name_norm` becomes `\u0001deleted:<tagId>`. The plain unique index frees the name at once, and H2 (tests) has no partial indexes. The original `name` is kept for audit |
| `entity_seq` in `entity_tags` | The reverse index `(tenant, tag, entity_seq)` gives keyset pagination in seq order, the same order and id space the bitmap index uses |
| Identity columns, not `SERIAL` | Standard SQL; portable to H2 and any PostgreSQL |
| Hash partitioning of `entity_tags` only | It's the only table that reaches billions of rows per shard. 16 partitions keep each under ~100M rows, so autovacuum and reindex stay quick |
| `COLLATE "C"` on keys | Byte order is identical on every OS and libc. A locale-collated index can silently corrupt after an OS upgrade changes collation rules, and `LIKE 'pre%'` only uses an index under `C` |
| `fillfactor` 90 / 70 | Free space per page so updates of `version` and `cnt` are HOT (no index churn) |

### 1.2 PostgreSQL tuning per shard

```
shared_buffers = 25% RAM            effective_cache_size = 70% RAM
max_connections = 400 (+ PgBouncer in transaction mode in front if pods × pool > 400)
autovacuum_vacuum_scale_factor = 0.02 on entity_tags_p*, outbox      (big tables vacuum sooner)
autovacuum_vacuum_cost_limit = 2000
idle_in_transaction_session_timeout = 30s                             (belt and braces for §5.1)
wal_level = logical                                                   (DR, tenant moves, optional Debezium)
synchronous_commit = on, synchronous_standby_names = 'ANY 1 (b, c)'  (RPO 0; one slow standby can't stall commits)
```

**PgBouncer caveat**: transaction pooling is fine (the service uses no session state, no prepared
statements across transactions, and no advisory locks). Set `prepareThreshold=0` on the JDBC URL.

The PostgreSQL JDBC driver must **not** use `reWriteBatchedInserts=true`: it reports
`SUCCESS_NO_INFO` per row, and `JdbcTagStore` needs per-row counts to know which tags were newly
attached. The store fails fast if it sees that mode.

### 1.3 Read queries (the ones that matter)

```sql
-- tags of an entity (PK range)
SELECT tag_id FROM entity_tags WHERE tenant_id=:t AND entity_type=:type AND entity_id=:id;

-- entities of a tag, keyset page (ix_entity_tags_by_tag, no sort)
SELECT entity_type, entity_id, entity_seq FROM entity_tags
 WHERE tenant_id=:t AND tag_id=:tag AND entity_seq > :after [AND entity_type=:type]
 ORDER BY entity_seq LIMIT :limit + 1;

-- boolean search fallback: all / any / none
SELECT et.entity_type, et.entity_id, et.entity_seq
  FROM entity_tags et
 WHERE et.tenant_id=:t AND et.tag_id IN (:all) AND et.entity_seq > :after
 GROUP BY et.entity_type, et.entity_id, et.entity_seq
HAVING COUNT(*) = :allCount
   AND EXISTS     (SELECT 1 FROM entity_tags a WHERE a.tenant_id=:t AND a.entity_seq=et.entity_seq AND a.tag_id IN (:any))
   AND NOT EXISTS (SELECT 1 FROM entity_tags n WHERE n.tenant_id=:t AND n.entity_seq=et.entity_seq AND n.tag_id IN (:none))
 ORDER BY et.entity_seq LIMIT :limit + 1;
-- (when `all` is empty the driving set is `any`; the planner drives from the smallest list)

-- autocomplete
SELECT * FROM tags WHERE tenant_id=:t AND name_norm LIKE :prefix || '%' AND name_norm > :after
 ORDER BY name_norm LIMIT :limit + 1;

-- usage
SELECT tag_id, SUM(cnt) FROM tag_usage WHERE tenant_id=:t AND tag_id IN (:ids) GROUP BY tag_id;
```

The SQL search is O(size of the `all` posting lists). With a 5M-entity `all` term it reads 5M index
entries: tens of seconds. That's the reason for the bitmap index (README §13). The SQL path is
the fallback, the STRONG path, and the oracle in `TagSearchIndexContractTest`.

## 2. Capacity and sizing

### 2.1 Inputs

| | Value | Source / assumption |
|---|---|---|
| Tenants | 300k | Cloud sites |
| Entities tagged | 4B | ~13k per tenant average, whales 50M+ |
| Assignments | 20B | ~5 tags per tagged entity |
| Tags | 300M | ~1k per tenant average, cap 10k |
| Reads | 300k QPS peak | 95% tags-of-entity (rendered on each issue/page view) |
| Writes | 30k QPS peak | edits + automation + imports |
| Searches | 5k QPS | JQL/CQL "labels = x" and filter UIs |

### 2.2 Storage

| Table | Row | Index | × rows | Total |
|---|---|---|---|---|
| `entity_tags` | ~110 B (heap, with tuple header) | PK ~70 B + by-tag ~45 B | 20B | **~4.5 TB** |
| `entities` | ~90 B | PK ~70 B + seq ~40 B | 4B | ~0.8 TB |
| `tags` | ~150 B | ~100 B | 300M | ~75 GB |
| `tag_usage` | ~50 B | ~40 B | 300M × ≤16 | ≤ 0.4 TB (most tags touch 1–3 buckets) |
| `outbox` | ~400 B | ~20 B | depends on retention | see below |

**Outbox retention**: 7 days at 30k/s peak is far too much to keep in the database. In practice the
average write rate is ~5k/s, and `OutboxRelay.prune()` deletes relayed rows older than
`tagging.relay.outbox-retention`. With 24 h retention: 5k/s × 86 400 × 420 B ≈ **180 GB**
cluster-wide, ~11 GB per shard. Kafka (7-day retention) is the replay log; the outbox only has to
cover relay outages. Set `outbox-retention: 24h` in production.

Total ≈ **6 TB** primary data. With 16 shards: ~375 GB per shard, plus replicas.

### 2.3 Shards

| Constraint | Per shard (r6i.4xlarge / n2-standard-16 class, 16 vCPU, 128 GB) | Shards needed |
|---|---|---|
| Storage | ≤ 1 TB comfortable (vacuum, restore time < 1 h) | 6 TB → 8 |
| Write transactions | ~5k tx/s sustained with synchronous standby | 30k → 6 (+ headroom → 12) |
| Primary reads (**all** reads are STRONG, no cache) | ~80–100k point reads/s on 32 vCPU (one PK range, buffer hit, ~10–20 µs CPU each) | 300k → 4; at 16 shards ~19k/s each ≈ 20–25% |
| Working set | entity PK + by-tag index hot portion ≈ 100 GB per shard | 256 GB RAM each at 16 shards |

**Plan: 16 shards** (headroom for 2× growth before splitting) of 32 vCPU / 256 GB, each a primary +
2 synchronous-quorum standbys (`ANY 1`) in the other two zones. Standbys are for durability and
failover only; no request reads them. Whales over ~200M assignments get a dedicated shard.

Per-shard load at peak: ~19k reads/s + ~1.9k write tx/s + ~300 searches/s (a ~0.1 ms barrier
probe each, plus page resolution). Expected latency on the primary: reads p50 ~2 ms, p99 < 10 ms;
writes p50 ~5 ms, p99 < 50 ms (the sync commit adds one cross-zone round trip, ~1–2 ms).

### 2.4 Pods

- Every read is a primary round trip, so a pod is I/O-wait bound, not CPU bound: ~2.5k reads/s per
  vCPU (JSON, routing, JDBC). 300k QPS → ~120 vCPU; with headroom: **40 pods × 4 vCPU**, Hikari
  pool 20 per shard per pod (800 connections per shard, multiplexed by PgBouncer onto ~200).
- JVM heap per pod: the bitmap index (below) plus small opt-in caches. **8 GB heap, 12 GB
  container**.

### 2.5 Bitmap index memory

A posting list over a tenant's `entity_seq`s. Seqs come from a shard-wide identity, so one tenant's
seqs are interleaved with others': for a mid-size tenant they're sparse (Roaring array containers,
~2 bytes per posting); for a whale they're denser (bitmap containers, ≤ 8 KB per 65 536 seqs).

| Tenant | Postings | Roaring size |
|---|---|---|
| Typical (13k entities × 5 tags) | 65k | ~130 KB |
| Large (1M × 5) | 5M | ~10 MB |
| Whale (50M × 3) | 150M | ~100–300 MB |

`tagging.index.max-tenants: 1000` with a mix of tenants ≈ 1–3 GB per pod. Whales go to dedicated
index pods (a separate Deployment that routes `/v1/search` for those tenants), so their memory
doesn't evict everyone else.

### 2.6 Kafka

30k events/s peak × ~400 B = 12 MB/s in. Every pod reads the topic (broadcast group): 40 pods ×
12 MB/s = 480 MB/s out, which is fine for a 6-broker cluster. **48 partitions**, key = `tenantId`
(per-tenant order), replication 3, `min.insync.replicas=2`, retention 7 d, compression `zstd`
(JSON compresses ~5×).

Shared (committed) consumer groups, each read once cluster-wide: `tagging-purge`, `tagging-trends`
(§16) and `tagging-analytics` (§17). Each has its own offsets, so one slow consumer never delays another.

If the broadcast fan-out grows (hundreds of pods), shard the index: route searches by tenant hash to
a fixed set of index pods and have only those consume the relevant partitions (static assignment).

### 2.7 What is deliberately not sized

| Store | Why it's absent from the request path |
|---|---|
| Redis entity cache | A strong cache needs synchronous invalidation before commit, and Redis's asynchronous replication can lose an invalidation on failover. The primaries have the headroom (§2.3), so the cache isn't needed. Redis appears only behind Envoy for global rate-limit counters |
| Async read replicas | They lag, so a read from one is stale by definition. The scale-out path is standby reads behind an LSN barrier (§5.8) |
| Trend store, analytics DB | Off the strong path by design: eventual consumers of the topic with their own databases (§16 ~15 GB, §17 ~6 TB/year) |
| OpenSearch | Product full-text search consumes our events downstream (~0.8 TB for 4B docs, owned by the product's search team); it is not part of this service's read path |

## 3. NoSQL alternative: Cassandra / ScyllaDB key design

The documented escape hatch if a single PostgreSQL shard's write rate ever becomes binding and
adding shards stops being attractive. CQL runs identically on self-managed Cassandra or Scylla (on
any Kubernetes), DataStax Astra, Scylla Cloud, and protocol-compatible managed services.

```sql
-- Tag definitions
CREATE TABLE tags (
  tenant_id text, tag_id bigint, name text, name_norm text, color text, version bigint, deleted boolean,
  created_at timestamp, updated_at timestamp,
  PRIMARY KEY ((tenant_id), tag_id));                     -- one partition per tenant, ≤ 10k rows

-- Name uniqueness: a "name lock" row, written with LWT
CREATE TABLE tag_names (
  tenant_id text, name_norm text, tag_id bigint,
  PRIMARY KEY ((tenant_id), name_norm));
-- INSERT INTO tag_names ... IF NOT EXISTS;   then INSERT INTO tags ...

-- Forward: tags of an entity
CREATE TABLE tags_by_entity (
  tenant_id text, entity_type text, entity_id text, tag_id bigint, created_at timestamp,
  PRIMARY KEY ((tenant_id, entity_type, entity_id), tag_id));

-- Reverse: entities of a tag, bucketed so a hot tag is 16 partitions, not one
CREATE TABLE entities_by_tag (
  tenant_id text, tag_id bigint, bucket smallint, entity_seq bigint, entity_type text, entity_id text,
  PRIMARY KEY ((tenant_id, tag_id, bucket), entity_seq))
  WITH CLUSTERING ORDER BY (entity_seq ASC);
-- bucket = murmur3(entity_type + entity_id) % 16

-- Dense ids for bitmaps (LWT on first sight of an entity, or a per-tenant hi/lo allocator)
CREATE TABLE entity_seqs (tenant_id text, entity_type text, entity_id text, entity_seq bigint,
  PRIMARY KEY ((tenant_id, entity_type, entity_id)));

-- Counters cannot be in a logged batch with regular tables
CREATE TABLE tag_usage (tenant_id text, tag_id bigint, cnt counter, PRIMARY KEY ((tenant_id), tag_id));
```

**Attach** becomes: a logged batch of `tags_by_entity` + `entities_by_tag` rows (atomic: all or
none eventually applied, but not isolated), a separate counter update (not idempotent: a retry
double-counts, so counters need periodic reconciliation), and events from CDC (Cassandra CDC or
Scylla CDC → Kafka) instead of an outbox.

**What you lose vs PostgreSQL** (why it's not the default):

| Guarantee | PostgreSQL | CQL |
|---|---|---|
| Name unique per tenant | Unique index | LWT (4 round trips, Paxos), and orphan `tag_names` rows on partial failure |
| ≤ 100 tags per entity | Exact | Read-then-write race, or LWT on a per-entity counter |
| Idempotent counters | Same transaction as the insert | Counters aren't idempotent; reconcile |
| Event exactly matching the commit | Outbox in the transaction | CDC (good) or dual write (bad) |
| Read-your-writes | Token + watermark | `QUORUM` writes + `QUORUM` reads (higher latency), no global seq |
| Boolean search | SQL fallback | None: the bitmap index is mandatory |

The SPI makes this a store swap: a `CassandraTagStore` must pass `TagStoreContractTest` and report
its real `capabilities()` (no `ATOMIC_OUTBOX` → the service would read events from CDC instead).

## 4. Write path in detail

### 4.1 Attach (single entity), statement by statement

```
BEGIN  (READ COMMITTED, statement timeout from the 10 s transaction timeout)
 1. for name in sorted(tagNames):                        -- sorted → unique-index locks in fixed order
      SELECT * FROM tags WHERE tenant_id=:t AND name_norm=:n
      if absent: SELECT COUNT(*) live tags (≤ 10k) ; INSERT INTO tags ...   → TAG_CREATED queued
 2. SELECT * FROM tags WHERE tenant_id=:t AND tag_id IN (:ids)              -- requireLive
 3. INSERT INTO entities (...) ON CONFLICT DO NOTHING
    SELECT entity_seq FROM entities WHERE ... FOR UPDATE                    -- the per-entity lock
 4. SELECT tag_id FROM entity_tags WHERE <entity>                           -- current set
    SELECT * FROM tags WHERE tag_id IN (current ∪ wanted)                   -- count only live ones
    if live > 100 → LimitExceededException (rollback)
 5. INSERT INTO entity_tags (...) VALUES (...) ON CONFLICT DO NOTHING       -- batch; counts = added
 6. for tag in sorted(added): UPDATE tag_usage SET cnt=cnt+1 WHERE ... bucket=:rand
                              (0 rows → INSERT ... ON CONFLICT DO UPDATE)
 7. INSERT INTO outbox (...) per event                                       -- last, so seqs are taken late
COMMIT (waits for 1 of 2 standbys) → token = shard:last seq ; evict any opt-in L1 entry on this pod
```

**Lock order** (deadlock freedom): tag-name unique entries (sorted) → entity rows (sorted, for bulk)
→ counter rows (sorted by tag id) → outbox (no conflicts, identity). Every write path takes them in
this order, so a wait-for cycle is impossible. PostgreSQL still detects deadlocks if a future change
breaks this; `CannotAcquireLockException` and `DeadlockLoserDataAccessException` map to 503 +
`Retry-After: 1` (`ApiExceptionHandler`).

### 4.2 Why the outbox insert is last

The relay can only advance past seq *n* when *n* has committed or rolled back. The longer a
transaction holds an allocated seq, the longer the shard's relay may wait behind it. Appending last
keeps the window to "the end of the transaction plus commit".

### 4.3 Bulk attach

Same as above for each entity, in sorted `(type, id)` order, inside one transaction, with:

- the idempotency key **claimed first** (`INSERT INTO idempotency_keys ... response = ''`): a
  concurrent request with the same key blocks on the unique index, then fails with a duplicate key
  and replays the winner's stored response. It never allocates outbox seqs.
- one sorted counter update for all deltas;
- the response stored with `completeIdempotency` before commit.

500 entities × 50 tags = 25k rows: ~200–400 ms on a warm shard. It takes 500 permits from the
tenant's write limiter and one slot of its bulk bulkhead.

### 4.4 Tag update and delete

```sql
UPDATE tags SET name=:n, name_norm=:norm, color=:c, version=version+1, updated_at=:now
 WHERE tenant_id=:t AND tag_id=:id AND version=:expected AND deleted=FALSE;   -- 0 rows → 412 or 404
```

Delete is the same update with `deleted=TRUE, name_norm='\u0001deleted:<id>'` plus a `TAG_DELETED`
event. `TagPurgeJob` (shared consumer group) then runs
`DELETE FROM entity_tags WHERE ctid IN (SELECT ctid ... LIMIT 1000)`-style batches through
`UnitOfWork.purgeAssignments(tagId, 1000)` until none are left, then deletes the counters. Batching
keeps each transaction short and the WAL rate bounded.

## 5. Consistency proofs and race analysis

Notation: *seq(e)* is the outbox seq of event *e*; *R* is `outbox_relay_state.last_seq`; *A(p)* is
the applied watermark of projection *p*.

### 5.1 Invariant I1: R is an exact watermark

> Every event with seq ≤ R is committed (or permanently rolled back), and every committed event with
> seq ≤ R has been delivered.

The relay reads rows with seq > R in seq order and stops at the first gap unless the next row is
older than `gapTimeout`. A gap at seq *g* with a younger row behind it means *g* is either still in
flight or rolled back. Waiting resolves the first case.

**Why an aged gap is safe to skip**: write transactions have a 10 s timeout
(`JdbcTagStore.WRITE_TIMEOUT_SECONDS`), and `TaggingProperties.Relay` refuses a `gapTimeout` ≤ 10 s.
Seq *g* was allocated before the later row *r* (identity order), so *g*'s transaction was already
running when *r* was inserted. *r* is older than `gapTimeout` (30 s), so *g*'s transaction has been
running for more than 30 s, three times the limit at which it is cut. It has therefore ended. Had it
committed, the relay's query would have returned *g*; so it rolled back, and *g* will never appear.

**Residual risks**, and their mitigations:

| Risk | Effect | Mitigation |
|---|---|---|
| Clock skew between the writer pod (stamps `created_at`) and the relay pod (computes the cutoff) > 20 s | A young gap looks old and is skipped while *g* can still commit | NTP/chrony on every node (cloud skew is ms); alert on `node_timex_offset_seconds > 1`. Upgrade path: stamp with DB `clock_timestamp()` |
| Commit stalls > 30 s after the last statement (sync standby unreachable, I/O freeze) | Same as above | `synchronous_standby_names` with `ANY 1 (a, b)` so one slow standby can't stall commits; alert on commit latency |
| Spring's timeout bounds statements, not the `COMMIT` itself | Same | As above |

The **upgrade that removes the timeout entirely** (PostgreSQL-specific, kept behind the store SPI):
store `pg_current_xact_id()` with each outbox row and relay only rows whose xid is below
`pg_snapshot_xmin(pg_current_snapshot())`. Every transaction older than that horizon has finished,
so gaps below it are proven rollbacks, with no clock involved. Every skipped seq is logged at WARN
(`skipping outbox seqs a..b`); alert if the rate is non-zero outside deploys or failovers.

### 5.2 Invariant I2: projections equal a prefix of the history

> For every projection *p*, its state equals the result of applying all events with seq ≤ A(p) (for
> its tenant) to the empty state.

Per tenant, events reach a projection in seq order: the relay publishes in seq order, Kafka
preserves order within a partition, and the key is `tenantId`. Each projection ignores events with
seq ≤ A(p) (redeliveries) and sets A(p) = seq after applying. Attach and detach are set operations on
(entity, tag), and for a given pair the events are ordered by the entity row lock, so applying them
in seq order reproduces the final set.

### 5.3 Index bootstrap: no missed event

The index has two sources: the snapshot (S = R as read in the snapshot transaction, plus all postings
visible to it) and the event stream. An event *e* of tenant *T* must end up in exactly one (or both,
deduped):

1. The tenant's state is created in LOADING **before** the snapshot. From then on, every delivered
   event of *T* is buffered.
2. Events delivered **before** the state existed are not buffered. Their data committed before the
   relay read them, so before delivery, so before the snapshot began: the snapshot contains their
   effect.
3. The snapshot may also contain effects of events not yet delivered (seq > S). They arrive later and
   are applied again. That converges because, for one (entity, tag) pair, commit order equals seq
   order: the entity row lock is held until commit and the seq is allocated last, so a later writer
   of the same entity allocates its seq only after the earlier one committed.
4. **S ≥ D**, where D is the highest seq this pod has seen delivered for the shard (read right after
   the state is created). This makes the watermark claim direct: everything this pod has been handed
   so far is ≤ S and covered by the snapshot, so A = S never trails an event a caller may already
   have observed through this pod. If S < D (a relay transaction delivered but hasn't committed R
   yet), retry; the relay commits within milliseconds, and there are up to 20 tries.
5. Install the snapshot with A = S, replay the buffer skipping seq ≤ S, and switch to READY.

`RoaringInvertedIndexTest` covers both branches: a buffered event during loading, and refusing a
snapshot with S < D.

### 5.4 Opt-in SESSION reads

Not on any default path: a read is STRONG unless the caller asks for `SESSION` or `EVENTUAL`
(exports, analytics). A write returns token *t* = seq of its last event. For a read with token *t*:

| Source | Accepts if | Why it's correct |
|---|---|---|
| Replica | replica's copy of R ≥ *t*, **checked in the same transaction as the read** | Replicas apply WAL in commit order; R ≥ *t* on the replica means the commit of *t* (which precedes the R update) was applied. Same transaction → same replica, even behind a load-balanced reader endpoint |
| L1/L2 cache entry | entry.asOfSeq ≥ *t* | asOfSeq is R read **before** loading the value, so the value includes everything ≤ asOfSeq |
| Index | A(tenant) ≥ *t* (wait ≤ 50 ms) | I2 |
| Otherwise | primary | |

**Cache fill race.** Reader X loads an entity at asOf = 100. Writer W commits seq 105 and evicts the
key. X then puts its (stale) entry. Without protection the stale entry would live until the TTL. The
eviction at 105 leaves a **tombstone(105)**; a put with asOf < 105 is dropped (`VersionedCache`).
Tombstones expire after `tagging.cache.tombstone-ttl` (5 min), far longer than any read.

**Tokens from reads.** The hot read path does not hand out the shard-wide R it observed as a token.
R covers every tenant on the shard, whereas the index watermark is per tenant; a client holding R
would make every SESSION search wait for events that never come for its tenant. Reads echo the
client's own token instead.

### 5.5 Tenant moves and tokens

A token names its shard. If a tenant's directory entry changes shards, a SESSION read with an
old-shard token is served STRONG from the new primary (`Reads.preference`). The index sees an event
from a different shard than the one it loaded from and drops the tenant (rebuilt on next search).

### 5.6 Per-entity limit under concurrency

Two attaches to one entity at 99 tags: both take `FOR UPDATE` on the entity row; the second blocks
until the first commits, then re-reads the current set (READ COMMITTED sees the committed 100) and
fails with 422. `AssignmentServiceTest` runs 8 concurrent attaches with a limit of 5 on an entity
holding 1 tag and asserts that exactly 4 succeed.

### 5.7 Delete vs concurrent attach (known gap)

`requireLive` reads the tag without a lock. If an attach reads the tag as live, a delete commits, and
the attach then commits, an assignment to a deleted tag exists. It's invisible (reads, the index and
search all filter deleted tags), but if the purge already finished, the row and its counter stay.
Mitigations, in order of cost: (a) a weekly reconciler that purges assignments of deleted tags (also
covers purges interrupted by a crash, since the purge consumer commits its offset when the purge is
*scheduled*); (b) `SELECT ... FOR SHARE` on the tags in `requireLive` (PostgreSQL only, and it makes
every attach take a share lock on a hot tag row).

### 5.8 Strong reads: proofs and scale levers

Default reads (no `consistency` parameter) are STRONG (`Reads.preference`). This section proves the
three mechanisms that make them linearizable and describes the one designed lever for scaling them.

**(a) Point reads on the primary.** A READ COMMITTED statement on the primary sees every transaction
that committed before the statement started. A write is acknowledged only after its commit, so a read
that starts after the acknowledgment sees it. Two reads in sequence see non-decreasing state. ∎

**(b) STRONG search through the index** (built: `TagSearchService`, `TagReader.latestSeq`,
`ix_outbox_tenant_seq`).

1. On the primary: drop the query's deleted or unknown tags.
2. On the primary: B = `SELECT MAX(seq) FROM outbox WHERE tenant_id = :t` (an index-only probe).
3. If the index's per-tenant watermark A ≥ B (waiting up to `tagging.consistency.index-wait`,
   50 ms), evaluate the bitmaps and resolve the page's entity refs on the primary. Otherwise SQL on
   the primary answers.

*Claim.* Every write W acknowledged before the search started is reflected in the answer.

*Proof.* W committed before step 2, so its outbox row is visible there and seq(W) ≤ B. By I2 (§5.2),
the index's state for the tenant equals all of the tenant's events with seq ≤ A applied in order. So
A ≥ B ≥ seq(W) implies W is applied. A tag deleted before the search is dropped in step 1 even if the
index hasn't applied the delete yet. Entity refs come from the primary. ∎

*Edge cases.*

| Case | Handling |
|---|---|
| The relay skipped a seq on the gap timeout (§5.1) | The skipped seq was a proven rollback under the timeout argument; the xid-horizon relay removes the timing assumption |
| The tenant has no outbox rows left (24 h retention) | B = 0. Any READY index has the tenant's data, unless the consumer-lag alert is firing; the runbook then disables index serving, so SQL answers |
| A tenant writing continuously | B runs ahead of A by the relay lag (10–60 ms), so its searches wait or fall back to SQL. A `LISTEN/NOTIFY`-woken relay shortens the lag (designed) |
| The index was bootstrapped from a snapshot | §5.3: A = S and S covers every delivered event |

**(c) Failover keeps linearizability.** Patroni / CloudNativePG hold the leader key in etcd or the
Kubernetes API with a TTL lease.

- Only a member of `synchronous_standby_names` is a promotion candidate. With `ANY 1 (b, c)` plus
  synchronous commit, every acknowledged commit is on the primary and on at least one candidate. The
  failover picks the candidate with the highest received LSN, which therefore holds every
  acknowledged commit. RPO is 0.
- The old primary demotes itself (stops accepting writes and reads) when it can't renew its lease,
  before the lease expires. The new primary is promoted only after expiry. With bounded clock drift,
  there is no instant at which both serve.
- An isolated old primary that hasn't yet noticed can't acknowledge writes either, because commits
  wait for a standby it can't reach. A read it serves in that window returns state that is current up
  to the last acknowledged write, because no newer write can have been acknowledged anywhere yet.
- PgBouncer and the pods follow the leader through the operator's service endpoint. In-flight
  requests fail with 503 and are retried by the client.

**(d) Tenant moves keep linearizability** (designed, §8). After the cutover a fence row
`tenant_fence(tenant_id, moved_to, epoch)` exists on the old shard, and every unit of work on that
shard reads it in its first statement (a PK probe on a tiny table). A pod with a stale directory
entry therefore fails with `TENANT_MOVED` instead of reading or writing the abandoned copy, then
refreshes the directory and retries on the new shard. Freezing writes during the cutover means the
new shard has every acknowledged write before the first read reaches it.

**(e) Scale lever: standby reads behind an LSN barrier** (designed, not built). This is used only if
one tenant's reads outgrow a primary; adding shards comes first.

1. A pod keeps one barrier fetcher per shard. A read that starts at time *t* joins the next
   `SELECT pg_current_wal_lsn()` issued on the primary after *t*, never one already in flight. At most
   one fetch is outstanding per shard per pod, which batches thousands of reads per round trip.
2. Read on a synchronous standby only once `pg_last_wal_replay_lsn() ≥ L`, checking it in the same
   session and waiting ≤ 5 ms. Otherwise read on the primary.
3. *Why it's linearizable:* a write acknowledged before *t* has its commit record at an LSN ≤ L,
   because L was read after *t*. A standby that has replayed past L shows it.
   `synchronous_commit = remote_apply` would make replay immediate, at a write-latency cost; `on`
   plus the wait is the usual trade.

It costs one batched primary round trip (~0.3 ms) per read and triples a shard's read capacity.

## 6. Failure modes

| Failure | Detection | Effect | Behaviour / recovery |
|---|---|---|---|
| Pod crash | K8s liveness | In-flight requests fail (clients retry: set ops are idempotent, bulk has keys) | Index rebuilt lazily on the new pod; its searches run SQL meanwhile |
| Shard primary down | Patroni / CloudNativePG leader lease (30–60 s) | Reads and writes for that shard's tenants fail with 503 + `Retry-After` | A synchronous standby is promoted with every acked commit (§5.8c). The identity may jump after failover (sequence cache): one gap, skipped after `gapTimeout` |
| One standby down | replication slot / `pg_stat_replication` | None: the quorum is 1 of 2 | Rebuild the standby; alert because the next loss blocks commits |
| Both standbys down | `pg_stat_replication` | Commits block, then time out (503); reads continue | Restore a standby. Never drop to async silently: that would break RPO 0 |
| Opt-in replica lag | `pg_replication_lag` (postgres_exporter) | Opt-in SESSION reads fall back to the primary | Automatic; alert if > 10 s. Default reads never use replicas |
| Kafka down | Producer errors in `OutboxRelay` | The relay keeps retrying; the outbox grows; projections on other pods freeze | Writes and point reads unaffected. STRONG searches miss the barrier and run SQL on the primary (slower, still correct). Outbox retention must exceed the longest tolerated outage |
| Kafka consumer stalls on a pod | consumer lag per pod | That pod's index and cache stop updating | `KafkaEventSubscriber` retries the listener with backoff and never skips a batch; the loop survives commit failures. Kill the pod if lag keeps growing |
| Relay stuck on a gap | `tagging_relay_lag_seconds` | Up to `gapTimeout` (30 s) of projection lag on that shard | Automatic. Sources: rollbacks after seq allocation (rare: the outbox insert is last, idempotency claims come first), sequence jumps after failover |
| Poison event (undecodable) | ERROR log | That pod's projections miss one event | Alert. The event is in the outbox and in Kafka; restart the pod to rebuild projections |
| Index bootstrap fails | WARN log | The store answers that tenant's searches | Retried on the next search |
| Hot tenant overload | 429 rate, bulkhead full | That tenant gets 429 | Others unaffected; raise the tier or pin to a dedicated shard |
| Trend store down | `tagging-trends` consumer lag | Trending endpoint 5xx after its cache expires; nothing else | Consumer retries without committing; counts catch up exactly once (§16.4) |
| Analytics DB down | `tagging-analytics` consumer lag | Dashboards stale | Catches up from Kafka (7 d budget) or the archive (§17.4) |
| Whole cell / region down | synthetic probes | Tenants of the cell are down | DR (§9) |

## 8. Moving a tenant between shards

Used to rebalance, isolate a whale, or drain a shard. Per tenant, online, with a short write pause.

1. **Copy**: on the target, `INSERT ... SELECT` every row of the tenant (or logical replication with
   a row filter `WHERE tenant_id = 'x'`, PostgreSQL 15+). Record the source outbox position P0
   before starting.
2. **Catch up**: replay source outbox events of the tenant with seq > P0 onto the target. These are
   idempotent set operations, so replaying is safe. Repeat until lag < 1 s.
3. **Freeze**: mark the tenant `MOVING` in the directory: writes return 503 + `Retry-After: 1`
   (typically < 2 s). Drain the last events.
4. **Cut over**: in one step, write the directory entry → target shard (bumping its `epoch`) and
   insert the **fence row** `tenant_fence(tenant_id, moved_to, epoch)` on the source shard. From then
   on, every unit of work for the tenant on the source fails with `TENANT_MOVED`. The pod refreshes
   its directory entry and retries on the target, so a stale pod can't read the abandoned copy
   (§5.8d, designed). `entity_seq` values differ on the target; every index sees events from a new
   shard and drops and rebuilds the tenant.
5. **Unfreeze**. Old SESSION tokens name the old shard and are served STRONG (§5.5).
6. **Clean up** the source rows after a safety window.

`StaticTenantDirectory` reads pins from config and computes the rest with rendezvous hashing. A
production directory is a small replicated table, `tenant_placement(tenant_id, shard_id, state,
epoch)`, cached in each pod with a watch. A tenant's row is written once at onboarding (rendezvous
hashing over the shards open for new tenants).

**Adding shards** then moves nobody: the new shard only takes new tenants, plus tenants moved
explicitly with the procedure above. With the config-based directory, adding a shard re-maps ~1/N of
the unpinned tenants, so pin every existing tenant first.

### 9.2 Cross-cloud DR

```
 AWS region (active cell)                              GCP region (warm standby cell)
 ┌─────────────────────────────┐   logical replication  ┌────────────────────────────┐
 │ PG shards s0..s15 ──────────┼───────────────────────▶│ PG shards s0..s15 (subs)   │
 │ Kafka tag-events ───────────┼── MirrorMaker 2 ──────▶│ Kafka aws.tag-events       │
 │ pods (active)               │                        │ pods (scaled to 2, read-only) │
 └─────────────────────────────┘                        └────────────────────────────┘
```

- **RPO**: logical replication lag (seconds). **RTO**: ~15 min (promote, flip DNS, scale pods).
- **Failover**: stop writes in AWS (if reachable); wait for replication to drain; promote the GCP
  subscribers (disable subscriptions; set identity sequences above the max seq + a safety gap, since
  logical replication doesn't copy sequence state); point the tenant directory at the GCP cell;
  scale the pods. Projections rebuild from the GCP databases. Tokens from AWS name AWS shards, so
  they're served STRONG.
- **Failback**: reverse replication, then the same steps.
- **Drills**: quarterly, per cell, with a tenant subset first (the directory makes per-tenant
  failover possible).

## 16. Trending tags

Built. README [§16](../README.md#16-trending-tags) is the overview; this is the schema, the proof and the operations.

### 16.1 Schema (own database, `db/trends/<vendor>`)

```sql
CREATE TABLE tag_activity (
    tenant_id VARCHAR(64) COLLATE "C" NOT NULL,
    grain     INT    NOT NULL,          -- 3600 (24 h window) or 86400 (7 d window)
    bucket    BIGINT NOT NULL,          -- floor(epoch_seconds(event.at) / grain)
    tag_id    BIGINT NOT NULL,
    attaches  BIGINT NOT NULL,
    CONSTRAINT pk_tag_activity PRIMARY KEY (tenant_id, grain, bucket, tag_id)
) WITH (fillfactor = 80);
CREATE INDEX ix_tag_activity_prune ON tag_activity (grain, bucket);

CREATE TABLE trend_progress (
    tenant_id    VARCHAR(64) COLLATE "C" NOT NULL,
    source_shard VARCHAR(64) NOT NULL,
    last_seq     BIGINT NOT NULL,
    updated_at   TIMESTAMPTZ NOT NULL,
    CONSTRAINT pk_trend_progress PRIMARY KEY (tenant_id, source_shard)
);
```

Flyway keeps this schema's history in `trends_schema_history`, so the tables can share a database
with a shard if an operator chooses (not recommended: the point is to keep this load off primaries).
At scale, range-partition `tag_activity` by `bucket` and drop partitions instead of `DELETE`.

### 16.2 Write: `JdbcTrendStore.record(sourceShard, events)`

One transaction per delivered batch:

1. Keep only `TAGS_ATTACHED` and `TAG_DELETED`; group by tenant, **in tenant order**.
2. Per tenant: `INSERT INTO trend_progress … (last_seq 0) ON CONFLICT DO NOTHING`, then `SELECT last_seq … FOR UPDATE`.
3. Drop events with `seq ≤ last_seq`. For the rest, add one per tag to `(grain, bucket(at), tag)` at every grain, and collect deleted tags.
4. Drop pending deltas of deleted tags. A deleted tag can't be attached afterwards (the attach checks liveness under the entity lock), so all of its deltas precede the delete.
5. Batched `UPDATE … SET attaches = attaches + :d`; batched `INSERT` for the cells that weren't there.
6. `DELETE` the deleted tags' rows; `UPDATE trend_progress SET last_seq = max(seq)`.
7. COMMIT. The Kafka offset is committed only after this returns.

**Exactly-once, informally.** Let `E` be the events of tenant `t` from shard `s` in seq order. The
relay delivers a prefix-closed, ordered sequence of `E` with repeats (at-least-once, in order per
tenant). Every applied event raises `last_seq` in the same transaction that counts it, so after any
commit the counts equal exactly the events with `seq ≤ last_seq`. A repeat has `seq ≤ last_seq` and
is skipped. Because delivery per tenant is in order, no event with a smaller seq can arrive *for the
first time* after a larger one has been counted, so the high-water mark loses nothing. (The relay
skips a seq only when it's a rollback, §5.1.)

Concurrency: the `FOR UPDATE` on the progress row serializes two consumers that both hold a tenant's
partition during a rebalance. Locking in tenant order prevents deadlocks between batches that cover
several tenants. Holding the progress row is also why step 5 needs no `ON CONFLICT` retry: nobody else
writes that tenant's cells.

Tenant moves: seq is per shard, so progress is keyed by `(tenant, source_shard)`. After a move the
new shard starts its own high-water mark; late events from the old shard still dedupe against theirs.

### 16.3 Read: `TrendingService.top`

```sql
SELECT tag_id,
       SUM(CASE WHEN bucket >= :first THEN attaches ELSE 0 END) AS cnt,
       SUM(CASE WHEN bucket <  :first THEN attaches ELSE 0 END) AS prev
FROM tag_activity
WHERE tenant_id = :t AND grain = :g AND bucket BETWEEN :from AND :last        -- :from = :first - window length
GROUP BY tag_id
HAVING SUM(CASE WHEN bucket >= :first THEN attaches ELSE 0 END) > 0                 -- popular
ORDER BY SUM(CASE WHEN bucket >= :first THEN attaches ELSE 0 END) DESC, tag_id
LIMIT :2n;
```

`rising` uses `HAVING cnt > prev` and `ORDER BY cnt − prev DESC, cnt DESC, tag_id` (written out as
aggregates, because PostgreSQL doesn't allow output aliases inside `ORDER BY` expressions). The
window ends at the current, partial bucket, so "24 h" means the current hour plus the 23 before it.
The service over-fetches `2n` rows, drops tags that aren't live (EVENTUAL `findTags` on the shard),
keeps `n`, and caches the result per (tenant, window, rank, limit) for `cache-ttl`.

Staleness budget: relay (~50 ms) + Kafka consumer lag (~1 s) + cache TTL (30 s). The response
carries `consistency: EVENTUAL` and `asOf`.

### 16.4 Operations

| Situation | Behaviour |
|---|---|
| Trend store down | Consumer retries the batch forever without committing; lag grows; `GET /v1/tags:trending` fails (5xx) once cached entries expire. Writes, reads and search are unaffected |
| Rebuild from scratch | Truncate both tables, reset group `tagging-trends` to the earliest offset; Kafka's 7 d retention covers the 7 d window |
| Late events (older than retention) | Counted into old buckets, removed by the next hourly `prune()` |
| In-process events (single node) | The aggregator is wrapped best-effort: a failed batch is logged and dropped rather than stalling the relay |
| Metric | `tagging_trending_events_total`; consumer lag of group `tagging-trends` |

Not covered: views or searches (only attaches count); detaches don't subtract; no per-entity-type
breakdown (add `entity_type` to the key if needed); `rising` is absolute growth, which favours big
tags (a smoothed ratio `(cnt + α) / (prev + α)` is the usual fix).

## 17. Analytics database

Designed, not built: it needs a consumer group, DDL and scheduled jobs, not service code.
README [§17](../README.md#17-analytics-database) has the overview and the raw-events DDL.

### 17.1 Tables

| Table | Engine | Sort key | Content |
|---|---|---|---|
| `tag_events` | `ReplicatedReplacingMergeTree(ingested_at)`, monthly partitions, TTL 25 months | `(tenant_id, toDate(at), shard, seq)` | Every event, deduplicated by (tenant, shard, seq) on merge |
| `tag_assignments` | MV from `tag_events`, `arrayJoin(tag_ids)` | `(tenant_id, tag_id, at)` | One row per (entity, tag) change, `delta = +1 / −1` |
| `tag_daily` | `ReplicatedSummingMergeTree`, TTL 5 years | `(tenant_id, day, tag_id, entity_type)` | `attaches`, `detaches` per day |
| `tags_dim` | `ReplicatedReplacingMergeTree(version)` | `(tenant_id, tag_id)` | name, deleted, created_at from a nightly snapshot of `tags` |

### 17.2 Correctness of the numbers

- **Raw events are exact** under `FINAL` (or `argMax` on the dedupe key): redeliveries share the sort key.
- **Live rollups may over-count** on a redelivery, because a materialized view sees each insert before merges deduplicate it. So:
  - a nightly job rebuilds each closed day: `INSERT INTO tag_daily_staging SELECT … FROM tag_events FINAL WHERE toDate(at) = yesterday()`, then `REPLACE PARTITION`;
  - dashboards label today **provisional**.
- **Current state** (tags of an entity, usage totals) is never answered here. That's the service's job, and it's strong.

### 17.3 Ingest, tenancy, deletion

- **Ingest.** Either a Kafka engine table plus an MV into `tag_events`, or Kafka Connect with the ClickHouse sink. Both use consumer group `tagging-analytics`. Insert in blocks of ≥ 100k rows or every 5 s.
- **Tenancy.**
  - Tenant-facing reports go through an API that sets `SQL_tenant`, and each table has `CREATE ROW POLICY tenant_only ON … USING tenant_id = getSetting('SQL_tenant') TO tenant_reader`.
  - Quotas are keyed by tenant.
  - Internal analysts have a separate role that may read across tenants, with access audited.
- **Deletion.**
  - Offboarding a tenant: `ALTER TABLE … DELETE WHERE tenant_id = ?` on every table, plus a drop of the Iceberg partition.
  - User erasure: `actor` is a pseudonymous id, rewritten by a weekly batched mutation.

### 17.4 Operations

| Situation | Behaviour |
|---|---|
| ClickHouse down | Group `tagging-analytics` lags; nothing else is affected. Kafka's 7 d retention is the outage budget; beyond that, replay from the Iceberg archive |
| Rebuild | Recreate tables; reset the group to earliest (7 d) and backfill older months from Iceberg |
| Schema change of `TagEvent` | Additive fields only (JSON); new columns get defaults |
| Sizing | ~430M events/day × ~40 B ≈ 17 GB/day compressed; 3 shards × 2 replicas, NVMe |
