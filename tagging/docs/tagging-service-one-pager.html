Designing a Tagging Service

An interview walkthrough: what the service does, how big it must be, which technology does what, how a request flows, how the data is stored, and how tag search works (inverted index, RoaringBitmaps, boolean operations). Based on tagging/README.md, tagging/INTERVIEW.md and the code, compared with "Design Tagging Service" on Medium.

1. Executive overview

The problem. Jira, Confluence and Bitbucket all let users put labels such as bug, p1 or release-7 on their items: issues, pages and pull requests. Instead of each product building its own, we build one shared tagging service. Products call it to create tags, attach tags to items, show the tags on an item, and find items by their tags.

What makes it hard.

  • Scale: 300,000 customer companies (tenants), 4 billion tagged items, 20 billion tag-to-item links, and up to 300,000 reads and 30,000 writes per second.
  • Correctness: if a user adds bug to an issue and refreshes, the tag must be there, every time, on every server. We can't serve stale data from a cache.
  • Fairness: a handful of huge customers (whales, with 50M+ items each) must not slow down everyone else.
  • Portability: it has to run on AWS, GCP or on-prem, so no cloud-only databases.

The design in three plain sentences.

#DecisionWhat it buys us
1Split the data by customer. Each customer's tags live entirely in one of 16 PostgreSQL databases (shards). The biggest customers get a shard of their own. Every request touches exactly one database, so every change is a simple, safe database transaction.
2Always read from the main copy of the database (the primary), and don't confirm a write until a backup copy in another data centre has it. Users always see their latest change, and a confirmed change survives losing a data centre. Splitting the data 16 ways makes this affordable: each primary runs at about 25% load.
3Keep a "tag → items" list for every tag (an inverted index), stored compactly in each server's memory, so that "issues tagged bug and p1 but not done" becomes a simple boolean AND / NOT of three lists. A query that would take seconds in plain SQL takes about 1 millisecond. Before using the in-memory copy, we check it has every confirmed change, so it is never stale (§6).
"I split the data by customer so every request is one transaction on one database. Every read goes to the primary, so users always see their own writes, and splitting 16 ways keeps each primary at a quarter of its capacity. The one query SQL is slow at is combining tags, so I keep, per tag, the set of item numbers that carry it. Then 'bug AND p1 AND NOT done' is just AND and NOT on three sets, which is about a millisecond in memory. I only use that copy when I can prove it's up to date."

Terms used on this page

Tenant
One customer company. All its data is kept together and never mixed with another's.
Entity / item
The thing being tagged: a Jira issue, a Confluence page, a pull request. We store only a reference such as jira:issue/10042, never the item itself.
Assignment
One link "item X has tag T". There are 20 billion of them.
Shard
One of 16 independent PostgreSQL databases. Each one holds a subset of the tenants.
Primary / standby
The primary is the copy of a shard that accepts reads and writes. Standbys are live copies in other data centres, ready to take over.
Strong consistency
Once a write is confirmed, every later read, from any server, sees it.
Forward index
Item → its tags ("what tags does JIRA-42 have?").
Inverted index
Tag → its items ("which issues have bug?"). It's the same idea as the index at the back of a book (word → pages), or a search engine's word → documents list.
Posting list
One entry of an inverted index: the list of items for one tag.
entity_seq
A small number (1, 2, 3, …) given to each item when it is first tagged, so that a posting list can be a set of numbers instead of long strings.
Bitmap
A row of 0/1 bits, one per item number: bit n is 1 if item n has the tag.
RoaringBitmap
An open-source library for compressed bitmaps. It stores a set of numbers in very little memory and still does AND / OR / NOT on millions of numbers in about a millisecond.
Outbox
A table where every change also writes an event row, in the same transaction. A relay then publishes those rows to Kafka, so no event is ever lost or invented.
seq
A number given to each change in a shard, in order (the outbox row's id). It only goes up, like a page number in the shard's history.
Watermark / read barrier
The watermark is the last change seq an in-memory copy has applied. The barrier is the tenant's latest change seq in the database. If watermark ≥ barrier, the copy is up to date.

2. Requirements and scale

What it must do (functional)

  • Manage tags: create, rename, change colour, delete. A name is unique within a tenant, ignoring case and spaces (Bug, bug and BUG are one tag).
  • Tag items: attach tags (by id, or by name, creating the tag if needed), remove tags, replace an item's whole set, and bulk-tag up to 500 items × 50 tags in one call.
  • Read: the tags of an item (by far the most common call: it runs on every issue or page view), the items with a tag (paged), and tag-name autocomplete.
  • Search: combine tags, e.g. all of bug, p1 and none of done, optionally only Jira issues.
  • Trending and analytics: "most-used tags this week" and adoption reports. These may be a few minutes old.
  • Not ours: who may edit an item (the product checks that before calling us), and full-text search of item content.

How well it must do it (non-functional)

What we provision: 16 shards (each 32 vCPU, 256 GB RAM, ~375 GB of data, ~2× headroom), each with 2 standbys in other zones, plus 40 stateless service pods (4 vCPU each).
The key insight: because sharding leaves every primary only 25% busy, we can afford to send every read to the primary. That is what makes strong consistency cheap, and it's why there's no cache.

3. Technology choices and why

One rule: open-source software with open protocols, run on Kubernetes or as a compatible managed service on any cloud (e.g. PostgreSQL as RDS / Cloud SQL / CloudNativePG, Kafka as MSK / Confluent / Strimzi).

"Why not put Redis in front?" A cache is a second copy that can be stale. To keep it exact, every write would have to invalidate it before confirming, and Redis can lose that invalidation on failover. We don't need it anyway: the primary is only 25% busy, and the hot read is a 1–2 ms index lookup.
"Why not Debezium (read the database log) instead of an outbox?" It gives the same guarantee. The outbox gives us business-level events, the per-shard seq the read barrier needs, and one less cluster to run. Debezium can be swapped in later without changing consumers.
"Don't we need Elasticsearch?" No, not in the tagging service. Elasticsearch (and OpenSearch) is an inverted index too, so it could answer bug AND p1 AND NOT done, but:
  • It breaks read-your-writes. A change becomes searchable only after a refresh (~1 s by default), after the Kafka lag, and there is no cheap way to prove "this index has every change up to seq 9001 for this tenant". The alternatives are making every write wait for a refresh (+~1 s) or returning stale results.
  • Its strengths go unused. Tag search is pure set algebra on integer ids: no text analysis, relevance ranking or fuzzy matching. That is exactly what a RoaringBitmap does, in ~1 ms, behind the watermark check.
  • It's a third copy to run. 4 B item documents in another cluster (shards, replicas, reindexing, upgrades), versus a few GB of RAM per pod rebuilt from Postgres.
Where it can still appear: outside this service. A product (e.g. Jira) that wants full-text search ("issues mentioning login timeout tagged bug") can feed its own OpenSearch index from our Kafka events, where ~1 s of lag is fine. The tagging service never reads it. I'd revisit if search grew into text + tags + many other fields with ranking, or if the product accepted eventually-consistent search.

How each kind of API call travels

Every request enters the same way: the product calls the ingress, which checks the user's login token and adds the tenant id taken from that token (never from the request body). Any pod can take the request. The pod applies the tenant's rate limit, then the shard router looks up which shard holds this tenant.

A. Write, e.g. attach bug to JIRA-42. The pod runs one transaction on the shard primary. It locks the item, checks the 100-tag limit, inserts the link, bumps the tag's usage counter, and writes an event row to the outbox. The primary confirms only after a standby in another zone has the change, and then the pod returns the item's new tag list.

B. Read, e.g. the tags of JIRA-42 (95% of traffic). This is one index lookup on the primary, in 1–2 ms. Because it's the primary, it always includes the latest write, whichever pod served that write.

C. Tag search, e.g. bug AND p1 AND NOT done. The pod asks the primary "what's the latest change number (seq) for this tenant?", which takes ~0.2 ms. If the pod's in-memory index has already applied that change, it answers from memory in ~1 ms. Otherwise it waits up to 50 ms for the index to catch up, then falls back to SQL on the primary, which is slower but exact.

D. Change events. The outbox relay publishes each shard's new outbox rows to Kafka in order, about 50 ms after commit. Four kinds of consumer read them:

  • each pod's index updater;
  • the trending counter;
  • the analytics loader;
  • the cleanup job that removes links to deleted tags.

All of them can be rebuilt by replaying Kafka.

E. Trending reads the trending database and says in its response that the result is a few minutes old. This is the only read that isn't strongly consistent.

The IX_ENTITY_TAGS_BY_TAG box is not a table. It is the inverted index stored in the database: a B-tree index on entity_tags (CREATE INDEX ix_entity_tags_by_tag ON entity_tags (tenant_id, tag_id, entity_seq)).   • tenant_id is first in every key, so a tenant's rows sit together on disk, and it's the shard key.
  • Deleting a tag just sets deleted. A background job removes its links in batches, so deleting a tag used 10M times returns instantly.
  • No foreign keys: they would lock the tag row on every attach. The transaction checks that the tag exists instead.
Why entity_seq is in both tables (a deliberate copy). entities owns the number: it assigns it once, when the item is first tagged. entity_tags keeps a copy on every link so that:
  • the inverted index (tenant_id, tag_id, entity_seq) can be built on this table and sorts a tag's items by number, so pages need no join and no sort;
  • a page of "items with tag T" returns entity_type, entity_id straight from the same rows;
  • the bitmaps can be bootstrapped with a single scan of entity_tags.
Why the copy can't drift: the number never changes and is never reused (no code updates or deletes an entities row). Every attach first reads the number under the item's row lock, then writes it into the new link, in the same transaction.
The normalized alternative: key entity_tags by (tenant_id, entity_seq, tag_id) and drop the string ids from it. That saves ~35 B per link (~0.7 TB across 20 B links), but the hot "tags of an item" call (285k/s) would need an extra lookup in entities first, and every page would join back to it.

6. Tag search: inverted index, bitmaps and boolean operations

6.1 Why we need an inverted index: the table is sorted the wrong way for search

entity_tags is sorted by item (its primary key starts with the item). That's perfect for the most common question, but useless for the reverse one. The running example on this page is one tenant with 8 Jira issues. When an issue is first tagged, the entities table gives it the next free number, entity_seq. Here JIRA-101 got 1, JIRA-102 got 2, and so on.

6.2 Boolean search is set algebra on the inverted index

Once each tag has its list of items (its posting list), every search is a combination of three set operations. The API's three fields map onto them directly:

API fieldMeaningSet operationBit operationExample
all: [a, b]has every one of these tagsintersection A ∩ BAND (1 only if both are 1)bug AND p1
any: [a, b]has at least one of these tagsunion A ∪ BOR (1 if either is 1)ui OR api
none: [a]has none of these tagsdifference R − AAND NOT (clear the bits that are 1 in A)… AND NOT done
entityTypeonly this kind of itemintersection with the type's setAND with the "all Jira issues" bitmap… AND jira:issue

The service evaluates them in this order (RoaringInvertedIndex.evaluate): result = AND(all) → AND OR(any) → AND NOT OR(none) → AND type. It then counts the 1-bits for the total, and reads the page of item numbers after the cursor.

6.3 Worked example: the same 8 issues, one bit per issue

A tag's bitmap is its posting list from §6.1 written as a row of bits. Column n is the issue whose entity_seq is n, and the bit is 1 if that issue has the tag. So bug's list 1, 2, 4, 5, 7, 8 becomes 1 1 0 1 1 0 1 1.

Query: POST /v1/search {"all":["bug","p1"], "any":["ui","api"], "none":["done"]}, which means "open p1 bugs in the UI or the API".

AND NOT (also called and-not or set difference, ③ − done) is two steps in one: flip the bits of done (NOT), then AND the result with ③. Per bit: 1 AND NOT 0 = 1 (keep), 1 AND NOT 1 = 0 (drop), and 0 AND NOT x = 0 (wasn't a match anyway). RoaringBitmap does this as a single andNot(③, done) call, and never builds the flipped bitmap, because "not done" would include every other item in the tenant.

Answer: numbers 2 and 7, total = 2 (just count the 1-bits). The pod turns the numbers of the page back into issues with one indexed query, entities WHERE entity_seq IN (2, 7), and returns [JIRA-102, JIRA-107]. You can check it against §6.1: both are p1 bugs touching ui or api, and JIRA-104 is left out because it is done. For the next page, the cursor is "after number 7".

Why this is fast. A CPU does AND / OR / AND NOT on 64 bits in one instruction. So a whale's tag with 10M items is ~156k instructions, a fraction of a millisecond, instead of reading 10M rows from disk.

The same query in SQL (the fallback) has to walk each tag's B-tree list and match them up:

SELECT entity_seq FROM entity_tags WHERE tenant_id=? AND tag_id = :bug
INTERSECT
SELECT entity_seq FROM entity_tags WHERE tenant_id=? AND tag_id = :p1
INTERSECT
SELECT entity_seq FROM entity_tags WHERE tenant_id=? AND tag_id IN (:ui, :api)
EXCEPT
SELECT entity_seq FROM entity_tags WHERE tenant_id=? AND tag_id = :done
ORDER BY entity_seq LIMIT 50;

That's correct, but on bug(5M) and p1(2M) and done(3M) it reads ~10M index entries (~450 MB), which takes seconds and loads the primary that serves every other read.

What "Roaring" adds: compression. A plain bitmap needs one bit per possible item, so a whale with 50M items needs 6 MB per tag, even for a tag on 3 items. With 10,000 tags that's 60 GB. RoaringBitmap fixes this:

  1. It splits the item numbers into chunks of 65,536 (numbers 0–65,535, 65,536–131,071, …).
  2. For each chunk it picks the smallest of three formats:
    • array, for few items: just the numbers, 2 bytes each (a tag on 3 items ≈ 6 bytes);
    • bitmap, for many items: a fixed 8 KB of bits;
    • runs, for long ranges: "items 1,000 to 40,000" in 4 bytes.
  3. Chunks with no items take no space.
  4. AND works chunk by chunk, and skips any chunk that is missing on one side.

Result: ~0.1–2 bytes per link instead of ~45 bytes in a B-tree. That's ~130 KB for a typical tenant, and 100–300 MB for a whale, so it fits in a pod's memory.

6.5 How the in-memory copy stays correct: the read barrier

The bitmaps are a copy, updated from Kafka about 50 ms after each change, so they could be slightly behind. We never let that show:

  1. Every change in a shard gets an increasing number, seq, in the outbox, committed with the change.
  2. Each pod's index remembers the last seq it has applied for each tenant (its watermark).
  3. Before a search, the pod asks the primary for the tenant's latest seq, the barrier (one tiny indexed query, ~0.2 ms).
  4. If watermark ≥ barrier, the copy includes every confirmed change, so it answers from memory.
  5. If not, it waits up to 50 ms for the copy to catch up, and otherwise answers with the SQL above. The response header X-Served-By: index | store says which one answered.

One user story, end to end (a Jira user labels an issue, then filters the board):

  1. The user types bu, and Jira calls GET /v1/tags?prefix=bu, which suggests bug.
  2. The user picks it. Jira calls POST /v1/entities/jira:issue/42/tags:attach {"tagNames":["bug"]}. In one transaction the service creates bug if it's new and attaches it. The response is the issue's new tag list.
  3. The page reloads and calls GET /v1/entities/jira:issue/42/tags. Whichever pod serves it reads the primary, so bug is there.
  4. The user filters the board, and Jira calls POST /v1/search {"all":["bug"],"none":["done"]}. The read barrier guarantees the result includes JIRA-42.
  5. The user opens "all bug issues", and Jira pages through GET /v1/tags/{bug}/entities?cursor=….
  6. About 50 ms after step 2, the same event reaches trending and analytics, plus any product that chose to consume it (e.g. its own full-text index).

Rules every call follows

  • Tenant from the token: the ingress sets X-Tenant-Id, so a caller can never reach another tenant's data.
  • Safe to retry: attach and detach are set operations, so doing them twice changes nothing. Only bulk attach needs an Idempotency-Key, so that a retry returns the same response.
  • Strong by default: callers can opt into consistency=EVENTUAL, for example for exports.
  • Paging uses an opaque cursor (the last item number seen) and a limit of at most 200.
  • Errors are standard problem JSON (RFC 7807). 429 and 503 carry Retry-After.
