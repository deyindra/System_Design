1. Executive overview

How the tree is storedEvery row stores its parent_id (the truth) and its path of ancestor ids /100/104/101/ (a read index)Breadcrumbs become one lookup and a subtree becomes one index range scan. The only cost is that a move rewrites the subtree's paths
Where it livesPostgres, sharded by tenant. One space sits on one shardEvery operation is one short ACID transaction on one database
How concurrency is safeA per-space lock: shared for creates, exclusive for moves. Edits use OCC (a version number). A large move uses a path-rewrite overlay and finishes in the background Thousands of creates run in parallel. Moves can't corrupt the tree or create cycles. Readers are never blocked

"I keep the parent pointer as the truth and a materialized path as the index, so the hot reads are one index operation. The hard part is moves, so I serialize them per space and use an overlay for big ones. Everything else runs concurrently."
Space / tree
A Confluence space or Jira project: one root and its descendants. The unit that moves are serialized on.
Adjacency list
Each row points to its parent (parent_id).
Materialized path
Each row stores the ids from the root down to itself, e.g. /100/104/101/. A subtree is every row whose path starts with a given prefix.
Breadcrumb
The ancestors from the root down to the node: Engineering › Runbooks › Architecture.
Keyset pagination
"Give me 50 rows after this key" instead of OFFSET. It's fast and stable while rows are being inserted.
LexoRank
Jira's sibling order. A position is a string, and inserting between two siblings picks a string between theirs, so no other rows change.
Advisory lock
A named in-memory Postgres lock, held until commit, available in shared or exclusive mode.
OCC
Optimistic concurrency control: UPDATE … WHERE version = 7. Zero rows updated means someone else changed the row first.
Overlay
A one-row rule, "paths starting with old really start with new", that readers apply while a large move's rows are still being rewritten.
LSN read token
The WAL position of your last write. A replica serves you only once it has replayed that far.

2. Requirements and scale

Functional

  • Create, get, rename and edit nodes
  • Children: paged, in user-defined order (lazy tree loading)
  • Breadcrumbs: root to node, shown on every page view
  • Subtree: optionally limited to depth N (sidebar, export, audits)
  • Move a subtree without ever creating a cycle; reorder among siblings
  • Trash, restore and purge a subtree
  • Inherited restrictions: a view restriction on an ancestor hides the whole subtree

Non-functional

  • About 25 reads per write. p99 under 20 ms for get, children and breadcrumbs
  • Strong consistency for structure: no cycles, orphans or nodes in two places. A writer always sees their own writes
  • Thousands of concurrent creates in one space. Concurrent moves from many admins
  • Strict tenant isolation. 99.95% availability. RPO 0

Also in each shard: outbox (events) and idempotency_keys.

CREATE TABLE nodes (
  tenant_id uuid, node_id bigint,      -- Snowflake id
  space_id bigint, parent_id bigint,
  path  text COLLATE "C" NOT NULL,     -- '/100/104/101/'
  depth smallint CHECK (depth < 64),
  rank  text COLLATE "C" NOT NULL,     -- sibling order
  node_type text, title text,
  status text DEFAULT 'ACTIVE',        -- or TRASHED
  version int DEFAULT 1,               -- OCC
  PRIMARY KEY (tenant_id, node_id));

-- children, keyset-paged
CREATE INDEX ix_nodes_children
  ON nodes (tenant_id, parent_id, rank, node_id);
-- subtree = prefix range scan
CREATE INDEX ix_nodes_path
  ON nodes (tenant_id, path);
  • tenant_id leads every key: isolation, locality, and a tenant can be moved to another shard as a unit.
  • The path holds ids, not titles: a rename touches one row.
  • The trailing / stops /1/2 from matching /1/23/.
  • COLLATE "C" makes LIKE 'p%' a plain B-tree range (verified on Postgres 16).
  • No child_count on the parent: that row would be a hot spot that every concurrent create waits on.
  • The body is in its own table, so the tree row stays small and cache-friendly.
  • Snowflake ids stay valid when a tenant moves to another shard.

6. High-level design

flowchart TB C[Browser, Jira and Confluence services] --> GW[Envoy gateway: auth, tenant routing, rate limits] GW --> TS[Tree Service: stateless pods] TS --> RC[(Redis: breadcrumbs, children page 1, titles)] TS --> PB[PgBouncer per shard] PB --> P[(Postgres primary, sharded by tenant)] P -->|sync| S[(Sync standby: RPO 0)] P -->|async| R[(Read replicas)] TS -->|reads with a read token| R P --> OB[Outbox relay] OB --> K[[Kafka: tree-events]] K --> MW[Move workers: batched path rewrite] K --> CI[Cache invalidator] K --> SE[Search, audit, webhooks] MW --> PB

Read flows

  • Breadcrumbs: split the path into ids, then WHERE node_id = ANY(ids). At depth 8 that's 8 PK probes in one round trip.
  • Children: WHERE parent_id = ? AND (rank, id) > cursor ORDER BY rank, id LIMIT 50.
  • Subtree: WHERE path > '/100/' AND path < '/1000' AND depth <= d. Path order is depth-first order.
  • Permissions: fetch restrictions for the path ids. The viewer must pass every restricted ancestor.
  • Trashed? Any ancestor on the path is TRASHED, so trash is O(1).

Write flows

  • Create: shared space lock, read the parent's path, insert with path = parent path + id, write the outbox. One transaction, about 2 ms.
  • Rename or edit: UPDATE … WHERE version = ?. No tree lock.
  • Reorder: new rank = LexoRank.between(prev, next). One row changes.
  • Move: exclusive space lock, cycle check, then a small move or a large move (§7).
  • Events: outbox → Kafka feeds search, audit, cache invalidation and move jobs, with no dual writes.

7. Deep dive: concurrency and moves

7.1 The lock matrix

OperationPer-space advisory lockOther protectionHeld for
Createsharedidempotency key~2 ms
Rename, edit, reorder, trashnoneOCC version~1 ms
Move ≤ 10k descendantsexclusivecycle check under the lock5–150 ms
Large move: accept / finishexclusiveone running job per space (unique index)~5 ms
Large move: each batchnonerow locks, SKIP LOCKED~20 ms

Shared locks never block each other, so 10k parallel creates in one space don't wait. Moves in different spaces run in parallel. A cross-space move locks both spaces in id order, so there's no deadlock. Every transaction sets lock_timeout = 2s, and a timeout returns 409 Retry-After.

7.2 Race 1: create vs move (why creates need the shared lock)

sequenceDiagram participant T1 as T1: create X under B participant DB as Postgres participant T2 as T2: move A (B is inside A) T1->>DB: read B.path = /r/A/B/ (old) T2->>DB: UPDATE rows LIKE '/r/A/%' (snapshot taken now) T1->>DB: INSERT X with path /r/A/B/X/, COMMIT T2->>DB: COMMIT (X was not in its snapshot) Note over DB: X keeps the old prefix and is lost from the tree
"In Read Committed, an UPDATE only re-checks rows it already saw, so a concurrently inserted child is missed. A row lock on the parent fixes only one of the two orderings. A shared/exclusive lock per space fixes both, and it costs creates nothing because moves are rare and short."

7.3 Race 2: move vs move (concurrent cycle)

Admin 1 moves A under B while admin 2 moves B under A. Each cycle check passes on its own snapshot, and together they create a loop. The exclusive lock serializes moves, so the second move sees the first and returns a 409 cycle error. The cycle check itself is one string test: newParent.path.startsWith(node.path).

7.4 Small move (≤ 10k rows): one statement

UPDATE nodes
SET path  = :new || substr(path, length(:old)+1),
    depth = depth + :delta
WHERE tenant_id = :t
  AND path LIKE :old || '%';
UPDATE nodes SET parent_id = :p, rank = :rank
WHERE tenant_id = :t AND node_id = :id;

Size is checked first with a LIMIT 10001 probe. 10k rows is about 3 MB of WAL, well under 200 ms.

7.5 Large move (> 10k rows): overlay plus background rewrite

  1. Accept (~5 ms, exclusive lock): update the root, insert move_jobs(old → new, RUNNING), bump tree_version. Return 202.
  2. Readers translate any path starting with old into new, so the tree looks fully moved immediately.
  3. Workers rewrite 1,000 rows per transaction with no tree lock, pausing if replicas lag. Rewritten rows leave the range, so a crashed job simply resumes.
  4. Finish (~2 ms, exclusive lock): no rows are left, so mark the job DONE and bump tree_version.

New children are created from the parent's translated path, so they're correct from the start. While a job is running, another move in the same space gets 409 Retry-After. Large moves stay inside one space. The worker starts on the MOVE_STARTED event and holds the job with a lease, which a sweep on any pod reclaims if that worker dies.

sequenceDiagram participant U as Admin participant TS as Tree Service participant DB as Postgres shard participant W as Move worker U->>TS: POST /nodes/101/move to 104 TS->>DB: lock, cycle check, size > 10k TS->>DB: update root + move_jobs RUNNING TS-->>U: 202 jobId (already looks moved) DB-->>W: MOVE_STARTED via Kafka loop until 0 rows remain W->>DB: rewrite 1,000 rows end W->>DB: lock, job DONE

7.6 Sibling order without a parent lock: LexoRank

To insert between ranks a5 and b, use ak. To append after i, use r. Only one row changes. Two concurrent inserts at the same spot may get the same rank, and that's fine because the index orders by (rank, node_id). When ranks under a parent grow past 32 characters, a background job respaces that parent's children.

8. Scaling reads

Replicas with read-your-writes

  • Every write returns X-Read-Token, which is its commit LSN.
  • The router sends a read to a replica whose replayed LSN is at least the token, otherwise to the primary. Lag is usually milliseconds, so the fallback is rare.
  • Readers without a token use any replica with less than 1 s of lag.
  • Strict reads always go to the primary: move pre-flight, create validation and OCC.

Redis with versioned keys

KeyInvalidated by
bc:{t}:{space}:{tree_version}:{node} ancestor idsa move bumps tree_version
ch:{t}:{parent}:{tree_version} children page 1DEL on create, reorder or trash under that parent
ti:{t}:{node} title, versionDEL on rename

Breadcrumbs store ids, not titles, so a rename invalidates one key. Readers holding a read token newer than the last move skip the cache.

9. Sharding, failures and trade-offs

Sharding

  • Shard by tenant_id. A space never spans shards, so every move is a single-shard transaction.
  • The tenant → shard map is cached in pods. A tenant is rebalanced with logical replication, a short write fence, then a map flip.
  • Tenants with more than 50M nodes get a dedicated shard.
  • Spanner or CockroachDB only if a tenant must be writable in several regions at once.

Failure modes

FailureHandling
Primary diesPatroni promotes the sync standby (RPO 0, under 30 s). Retries reuse the idempotency key
Replica lagsThe router drops it. Token holders use the primary
Redis downReads go to replicas. Correctness is unaffected
Move worker crashesThe overlay keeps reads correct. Another pod claims the job when its lease expires
Path drift (a bug)A nightly verifier rebuilds paths from parent_id with a recursive CTE

Follow-up questions to expect

"Why not a closure table?" It makes arbitrary ancestor joins easy, but it stores N × depth rows (about 30 B here), and a move deletes and inserts subtree × depth rows. A path gives the same reads more cheaply.
"Why not Neo4j?" A tree with tenant-scoped prefix queries doesn't need graph traversal, and it would add a second source of truth with no tenant sharding. Jira issue links do form a graph, and that's a separate service.
"What if a move touches 1M pages?" The overlay commits in milliseconds, and the background rewrite takes about a minute, throttled on replica lag. Readers never see a half-moved tree.
"Hot parent with 10k children created at once?" There's no parent row update and no parent lock. The space lock is shared, ranks can tie, and node_id breaks ties.
"Jira's fixed levels?" node_type plus a rules table (a sub-task only under a story) is checked at create and move time.
