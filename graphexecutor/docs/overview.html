Running Task Graphs in Parallel: From Threads in One JVM to Workers on Many VMs

Running a dependency graph of tasks in parallel: first across threads in one JVM, then across processes on many VMs, without changing the code you write.

The rest of this article shows how one design delivers this on threads in one JVM, and on worker processes spread across many VMs.

Build pipelines, data workflows, crawl plans and deployment rollouts share a shape: tasks with dependencies. An edge a → b means "a before b". The textbook answer is Kahn's topological sort: run whatever has no unfinished dependencies, then repeat. But a real graph is rarely one tangle. It's usually many independent subgraphs that never affect each other, and they're the easiest parallelism you'll find.

This article walks through graphexecutor, a small pure-JDK library built on that idea. It covers the single-VM design and how the same design stretches to a cluster of worker processes.

1. The key idea: find the independent groups first

Two tasks can affect each other only if some chain of edges connects them, in either direction. In a → c ← b, a and b never point at each other, but both feed c, so they belong together. The right unit is a weakly connected component, not a strongly connected one (that would wrongly split a and b).

One BFS over the graph, following edges both ways, finds every group in O(V + E). From then on each group is its own little topological run, and the groups run concurrently.

2. Single VM: multi-threaded by design

TaskExecutor is a template method. Its final submit owns the orchestration, and a subclass supplies the work. TopologicalTaskExecutor is the ready-made subclass for "a before b" graphs. Four decisions make it safe to run concurrently:

  • Snapshot before dispatch. Each group gets its own copy of its subgraph, made on the calling thread. Worker threads never read the shared, non-thread-safe graph, and the caller can modify it as soon as submit returns.
  • Validate everything before running anything. A dry run of Kahn's algorithm (counters only) detects cycles per group. With REJECT_GRAPH, one cyclic group means nothing runs. With ISOLATE_GROUP, only that group is rejected.
  • Parallel inside a group, too. A task is submitted the moment its last dependency finishes: Kahn's ready set, driven by completions. Counters live in one AtomicIntegerArray and adjacency in int[][]. Each decrement follows a task that is orders of magnitude slower, so contention on the counters is negligible.
  • Two pools, on purpose. Each group's coordinator blocks until its group finishes. If coordinators and tasks shared one fixed pool, the coordinators could take every thread and starve their own tasks, so the executor refuses a shared pool.

The node is the task. TopologicalTaskExecutor<T> is generic in the node type, and executeTask(T) receives the node itself, so a node can carry everything its work needs. Here a record does, and its equals/hashCode come from its fields:

record Step(String id, String command) { }

Step compile = new Step("compile", "mvn -q compile");
Step test    = new Step("test",    "mvn -q test");
Step pack    = new Step("package", "mvn -q package -DskipTests");
Step fetch   = new Step("fetch",   "curl -sO https://example.com/data.csv");
Step parse   = new Step("parse",   "python3 parse.py data.csv");

Graph<Step> g = Graph.directed();
g.addEdge(compile, test);      // compile before test
g.addEdge(test, pack);         // test before package
g.addEdge(fetch, parse);       // an independent group: runs alongside the build

ExecutorService groupPool = Executors.newFixedThreadPool(4);   // group coordinators
ExecutorService taskPool  = Executors.newFixedThreadPool(16);  // the tasks

TopologicalTaskExecutor<Step> executor = new TopologicalTaskExecutor<>(
        groupPool, taskPool, IneligibleGroupPolicy.ISOLATE_GROUP) {
    @Override
    protected void executeTask(Step step) throws Exception {
        // every step this one depends on has already finished
        Process p = new ProcessBuilder("sh", "-c", step.command()).inheritIO().start();
        if (p.waitFor() != 0) {
            // an exception fails this group only
            throw new IllegalStateException(step.id() + " exited with " + p.exitValue());
        }
    }
};

for (GroupResult<Step, List<Step>> r : executor.execute(g)) {
    String outcome = r.isSuccess() ? "done" : String.valueOf(r.error());
    System.out.println("group " + r.group().id() + ": " + outcome);
}

Failure is isolated. An exception becomes that group's GroupResult, and every other group still finishes.

3. Multi-VM: the same algorithm, as rounds

Past one machine, shared atomic counters stop working. The fix is the model Pregel popularized: bulk-synchronous rounds over shards. There are two questions: where each task lives, and who runs it when.

How the graph is sharded

  • A node's shard is a pure function of its key: shard = floorMod(key.hashCode(), SHARDS). String.hashCode is fixed by the JDK spec, so every VM computes the same answer without asking anyone. There's no directory of nodes to keep in sync.
  • The loader writes the shard onto each vertex in AGE or Neo4j, and indexes (shard, key). A worker then pages through only its own shards, a batch at a time. No VM ever holds the whole graph.
  • Edges may cross shards. That's expected. A cross-shard edge just turns into a message between rounds.
  • Workers lease shards, not nodes. Each worker claims up to SHARDS_PER_WORKER shards with a lease in the database and renews it with a heartbeat. If a worker dies, its leases expire and the survivors claim its shards. A shard keeps no state between rounds, so nothing has to be handed over.

How each scale uses them:

  • Single VM: none of them. The graph is an in-memory Graph, and the counters are an AtomicIntegerArray. If a stored graph turns out to be small, GraphStore.load reads it into a Graph for the single-VM executors.
  • Simulated partitions in one JVM (DistributedTopologicalExecutor): an in-memory CompletionLog, plus an in-memory transport in place of the ClusterStore.
  • Many VMs (Worker): all three, in a database every worker can reach. In practice that's the graph's own database, so the database is the network: workers never talk to each other directly. Tests use InMemoryGraphStore, InMemoryCompletionLog and InMemoryClusterStore, with threads standing in for VMs.

Split this way, each store gets the treatment it needs. The big, static graph is sharded and read in batches. The log is the only state that has to survive a crash. The small, hot coordination data can depend on the store's own clock and compare-and-set.

How dependencies are managed, without counters

Dependencies are simply the edges in the GraphStore, and progress is the CompletionLog. A task is ready when every one of its predecessors is logged DONE:

ready(v) ⇔ every u ∈ predecessors(v) has a DONE outcome from an earlier round

Each round, every shard runs the same six steps:

1. CANDIDATES  round 0: GraphStore.sources(myShard)    my tasks with no predecessors
               round r: ClusterStore.inbox(r-1, myShard) task keys other shards sent me

2. READY?      for each batch of candidates:
                 preds = GraphStore.predecessors(batch)
                 done  = CompletionLog.outcomes(preds)
               keep t if every predecessor is DONE from an earlier round
               otherwise drop t; nothing is remembered

3. RUN         executeTask(t) for each ready task (one by one on this shard's thread)

4. LOG         CompletionLog.record(t, DONE or FAILED, r)    before any message about t

5. NOTIFY      for each task that is DONE: GraphStore.successors(...)
               group the successors by owner shard = hash(key)
               ClusterStore.send(r, myShard, toShard, keys)  one batch per destination

6. ARRIVE      ClusterStore.arrive(r, myShard)
               ClusterStore.advance(r)   the first call that finds every shard
                                         arrived starts round r+1

A message is a hint, not a decrement. It means "this task of yours might be ready now". The receiver always checks the log for the real answer, so a duplicated or replayed message can't make a task run too early or twice.

Here is what happens when a dependency is late. test needs both compile and lint, and lint has to wait for codegen:

Each predecessor announces test once, when it finishes. Only the announcement from the last one finds everything DONE. There's no counter to keep, no waiting list, and nothing to lose in a crash. The rest follows from the same rule:

  • A failed predecessor sends nothing and is never DONE, so everything downstream of it never runs. Everything else carries on.
  • A cycle: each task on it waits for another one on it, so none ever becomes ready.
  • Two predecessors finishing in the same round both send "test?". The receiver reads the inbox as a set, so it checks test once.
  • The barrier keeps everyone consistent. "DONE in an earlier round" means no shard acts on a log entry while that round is still being written, so every shard sees the same answer.
  • Memory is the frontier, not the graph. A shard reads only its candidates, their predecessor lists and those predecessors' outcomes, all in batches.

What runs in parallel, round by round

Round r runs every task whose last dependency finished in round r−1. Within a round, every shard works at the same time: each worker gives each of its shards its own thread, and the workers are on different VMs.

Every row is the six steps above, run by four shards at once. test runs in round 1 because both compile and lint were logged DONE in round 0.

So parallelism comes at two levels: across VMs (workers) and across shards inside a VM (one thread per leased shard). The tasks a single shard has ready in a round run one after another on that shard's thread. To get more parallelism, use more shards than workers: shards are cheap, and they also spread a dead worker's load over several survivors.

  • Rounds = the longest dependency chain, not V. Nine tasks finish in 3 rounds. A wide, shallow graph with a billion edges finishes in a handful.
  • One batch per sender and receiver per round, not one message per edge. In the single-JVM simulation that batch is combined (v, −k) decrements.

No group finding across VMs

In one VM, the first step is a BFS that finds the independent groups. That needs the whole graph in memory, which is exactly what a graph too big for one VM doesn't allow. So the multi-VM run never computes groups, and it doesn't need to:

  • Independence falls out of the dependency rule. Each round runs every task whose dependencies are done, whatever group it's in. In the table above, groups A, B and C are never identified, yet compile, lint, fetch and notify all start in round 0 on four shards.
  • The shard replaces the group as the unit of parallelism. It's fixed by the hash at load time, so no VM has to see the graph first.
  • Failure is isolated per task, not per group. A failed task skips only the tasks downstream of it. Everything else keeps running, including the rest of its own group.
  • No up-front cycle check, because that would mean reading the whole graph too. Tasks on a cycle, and everything downstream of them, simply never become ready. They have no outcome in the log, and the report's done/failed/skipped counts leave them out.

Groups can still be found without one machine seeing everything. With label propagation, every node repeatedly adopts the smallest label among its neighbours, using the same rounds and combined messages. It takes about as many rounds as the graph's diameter, with no global BFS. The single-JVM simulation (DistributedTopologicalExecutor) uses this to place small groups whole on one partition, so they send no cross-partition messages. Across VMs, the shard is already fixed when the graph is loaded, so labels would only help if the loader sharded by component label.

Crashes need no checkpoints

A shard keeps nothing between rounds. Its candidates are in the ClusterStore inbox, and its answers are in the CompletionLog, which is written before any message about a task is sent. So if a worker dies, another one leases its shards and replays the round. Logged tasks aren't run again, and resent batches are dropped by their (round, from, to) key. The log is the only state that has to be durable.

Multi-VM: workers never talk to each other; all shared state goes through the store.

Each worker streams only its own shards from the database. The store enforces the cluster rules:

  • Leases on store time, not the worker's clock, so clock skew can't give a shard two owners.
  • Fenced arrivals: a worker presumed dead (in a GC pause, say) can't finish a round its replacement now owns.
  • No coordinator: advancing a round is a compare-and-set that any worker may call.

Kill a worker with SIGKILL mid-task and the survivors pick up its shards. The run still finishes, with exactly the rounds a single process computes.

// a worker process's main; config comes from the environment (DB_URL, SHARDS, ...)
try (AgeWorkerContext ctx = AgeWorkerContext.of(System.getenv())) {
    NodeCodec<String> codec = NodeCodec.strings();
    ClusterReport report = Worker.topological(
            myExecutor,                  // same DistributedTopologicalExecutor subclass
            ctx.graphStore(codec),       // sharded, read-only graph in AGE
            ctx.completionLog(codec),    // durable outcomes
            codec, ctx.cluster(), ctx.config()).run();
}

A middle step makes the jump safe. DistributedTopologicalExecutor runs the partitioned, round-based algorithm inside one JVM, with an in-memory transport. Each partition touches only its own state, so moving partitions onto machines swaps the transport, not the algorithm. The tests check that every scale gives the same answer.

Takeaways

  • Look for independence before you look for speed. Weakly connected components are free parallelism.
  • Snapshot and validate before dispatch. Concurrency bugs and half-run graphs both disappear.
  • Make state derivable. If the log can rebuild every counter, recovery is a replay, not a restore.
  • Let the store enforce the rules: leases, fencing and compare-and-set instead of a coordinator.
